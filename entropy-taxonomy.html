5. Implementation Priority

What to build in what order, based on entropy-per-effort
#FeatureImpactEffortWhy first?
1 Functions: body + signature fingerprinting (already have it) High Done Most common duplication: two functions that do the same thing
2 Interfaces & Type Aliases: member fingerprinting, alias resolution Very High Medium Type duplication is the silent entropy killer. Interface User = Interface Person with different names. Alias resolution catches the "UserId = string, CustomerRef = string" problem.
3 JSX Elements: structure fingerprinting with text/attr normalization High Medium Same card / same form / same list in multiple components. The frontend version of function duplication.
4 Object Literals: config object shape fingerprinting Medium Low Style objects, option bags, query configs. Small code, high leverage.
5 Hook Calls: callee + args fingerprinting Medium Low Same useState/useEffect/useQuery patterns with different variable names but identical structure.
6 Union overlaps: member-set intersection Medium Medium Status enums, discriminated unions that could be merged.
7 Cross-file aggregation: CLI that collects fingerprints across files Very High Medium This is where the real entropy lies — same helper in utils/a.ts and utils/b.ts.
8 Class structure: method + property fingerprinting Low Low Services/controllers with same shape. Lower priority if not OOP-heavy.
9 Template Literal: SQL/CSS/URL fingerprinting Low Low Niche but meaningful in certain codebases.
The central design tension: You're building a tool that tells developers "your code is too similar." But similarity isn't always bad — route files, test files, and config files look similar by design. The art is in distinguishing accidental duplication (should collapse) from intentional repetition (should stay). The configuration surface and the `skipGlobs`/`skipTests`/`skipGenerated` options are where this distinction lives.
